# 局部修补与架构调整的边界

这些原则来自项目早期设计与后续修复中的经验，用于判断改动范围。它们不是自动执行的重构计划。

## 何时转为由用户指导的设计讨论

以下变化通常超出局部修补：重新划分 session 与 checkpoint 职责、修改持久化协议或恢复语义、整体替换上下文结构、新增长期维护的摘要区域、改变宿主机与容器的信任边界。涉及文件不多，也可能是架构变化。

遇到这类需求，先整理现状、证据、最小替代方案、收益与代价，再交由用户确定方向。不要以“排查发现问题”为由自行重写系统。

## 状态与持久化

区分运行状态、可恢复快照与追加事件的职责。讨论恢复时，画清“发起工具 → 产生副作用 → 记录结果 → 保存恢复状态”的边界；跨文件写入不是天然事务。

恢复应区分已完成、待执行和执行结果不确定，不能用盲目重放掩盖缺失记录。设计变更需考虑旧数据兼容和中断窗口。

## 上下文治理

区分原始归档、当前投影、摘要与按需检索。每个区域应有明确职责、更新时机和失效依据；新增区域会占用正文预算，并带来更新与一致性成本。

先检查已有信息如何丢失或被误用，再考虑添加区域。短历史与长历史需要不同验证条件，受控重复内容的压缩效果不能直接当作真实任务收益。

摘要保存历史事实，不意味着所有历史规则仍然有效。来源正确也不保证模型对事实作出的当前推断正确。

## 执行隔离

将编排与执行分离有利于替换、销毁执行环境，但目录挂载、网络、权限、镜像和工具接口才是实际边界。不要仅因“运行在 Docker 中”就认定任何操作安全。

隔离副本与直接工作模式有不同的可见性、外部编辑和写回冲突语义。改变模式前先由用户选择预期行为，而不是用每次覆盖工作目录来解决同步问题。

## 设计方案需要回答的问题

新机制修复了哪项已证实缺陷？能否在现有机制中解决？新增状态由谁维护、何时失效？对上下文与 API 成本有何影响？如何兼容旧会话？怎样验证收益，并在无效时只撤销本次改动？
