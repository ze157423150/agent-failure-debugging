# 检查点恢复与对照复测

## 选择验证方式

| 方式 | 能验证 | 不能单独证明 |
|---|---|---|
| 单元/回归测试 | 状态机、校验、边界与确定性逻辑 | 真实模型会采取预期行动 |
| 记录响应回放 | 原工具参数序列在新代码上的结果 | 生成质量或真实调用量改善 |
| 真实模型复测 | 本次模型与工具的实际交互 | 普遍稳定性及全部收益的因果归属 |

按原缺陷选择最小有效验证，修复新问题后再扩大检查。没有明确需要时，不重复付费测试已通过任务。

## 准备独立实验

1. 选择失败轮次之前的可信边界，核验已有文件清单、校验和及状态一致性；不要绕过恢复保护来强行启动。
2. 复制到新目录，保留原数据，只调整必要路径。记录原始来源、代码版本、构建产物与镜像标识；条件变化需说明。
3. 保留相同用户输入、历史、工具、模型设置、预算和验收口径。冻结代码不等于供应商模型行为固定。
4. 将私有验收置于模型不可见的位置，必要时在一次性工作副本中运行，避免验收操作污染活跃会话。
5. 保存实际请求、响应、工具结果、异常和轮末状态；避免在日志中保存请求认证头、API Key 或私人数据。

如果没有检查点，使用能保留相关前提的最小复现，明确它与原现场的差异，不伪称完全恢复。

## 验收

核对任务实际产物，而非只相信最终回答或 COMPLETED 状态。检查用户输入、嵌入测试的数据、断言期望值和既有用例是否保留，并运行独立于模型生成断言的验收。

有意错误实现可用于验证验收能否检测回归，但是否采用取决于项目，不把它作为所有任务的固定要求。

## 反馈纠错验证

先确认授权目标是首次异常定位还是观察自动纠错，沿用用户指定的停止条件，不自行把“异常即停”改成继续运行。

- 确定性测试：构造一个已知可恢复的失败，检查原文件和状态未被错误改变、反馈进入下次请求，以及后续获取来源或更正操作能完成。对重复失败、预算耗尽及不确定副作用验证安全停止；脚本化模型的行为只能证明运行链路，不证明真实模型会正确选择。
- 真实模型验证：从安全失败状态继续并保留原反馈；若只能从更早边界重新运行，说明这不等价于原错误后的纠正。只开放完成当前修复所需的预算和工具，不注入正确补丁、期望值或私有测试答案。
- 独立验收：确认修复符合任务，不以删除测试、放松断言或改动受保护输入换取通过。人工直接修正后再跑测试，标记为人工修复验证。

记录错误出现在哪次调用、后续请求是否实际包含诊断、模型采取的修正和重测结果。分别统计首次成功与有纠错机会的失败样本恢复情况；把监控提前截断单列，不能将其算成已证明的纠错失败。记录额外调用、Token与耗时，而不只报告最终通过。

报告说明付费 API 次数是否含摘要，Token 来自供应商还是估算。跨运行比较采用相同口径，不把字符/字节缩减称为实际 Token 节省。

## 结束和记录

遵循用户的轮次、调用与 Token 停止条件。没有新证据的同一失败不自动无限重跑。

记录：恢复来源、实际版本、命令、模型与参数、停止条件、工具失败、任务测试、独立验收和仍未覆盖的路径。若模型本次首次就正确，说明它没有触发原错误修复路径；不能把全部调用下降归因于运行层改动。
