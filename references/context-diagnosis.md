# 上下文诊断

## 把“存着”与“看得见”分开

完整工具结果可能保存在事件日志或归档文件中，但模型只看到投影后的片段、摘要或索引。检查真实请求，而不是仅检查 session 内有无该条记录。

对关键事实记录：来自哪里、属于哪个时间点、是否被替代、当次请求中出现在哪里、正文是否完整。没有保存请求时，可以依据代码和快照重建，但必须说明它不等于原始发送证据。

## 失败后的反馈链路

沿“结果捕获 → 持久化 → 下次请求投影 → 模型调整 → 再执行/验证”定位断点。工具有失败事件，不等于模型已经看见失败；监控在下次请求前暂停，也不等于模型拒绝纠错。检查失败诊断是否被截断、过期过滤或摘要改写成错误结论，必要工具是否被隐藏。

反馈应按实际失败类型提供可执行的区别：文件已存在应更新；原文不足应按需读取；同组冲突应合并补丁；测试失败应核对契约、输入与断言。不要在不能确认原因时把某种修复当作事实，或把私有验收答案注入模型。

已确认未执行的操作可以重新生成；已确认成功的操作应复用结果；执行结果不确定时先按项目机制核验，不能为了“自动纠错”盲目重放有副作用的操作。网络重试、同上下文重新采样、基于失败反馈修正、回退检查点重启是不同机制，分别记录。

## 错误断言

独立核算业务期望值，确认参数顺序和数组索引。分别标出当前需求、规范、历史测试、历史助手回答和执行结果的用途：历史测试可能本身就是错误来源。

首次出错后，检查失败反馈是否给出了实际字段、期望值和实际值；检查下一次请求里这些信息是否仍完整。模型拥有足够信息仍改错，与反馈被截断或摘要漏掉，是不同问题。

不要把模型自己写的断言全部通过当作任务成功。检查是否通过改低标准、删除用例、篡改输入或让实现迎合错误断言获得通过。

## 重复读取

逐次列出路径、范围、版本指纹和调用目的，再核对前一结果在下一请求中是否可见。

- 文件刚被修改，旧读取失效：重新读取可能合理。
- 搜索或 diff 输出被截断，未包含目标范围：需要更准确定位。
- 需要的结果已被隐藏、只剩索引：检查检索工具是否可用、返回内容是否可用。
- 同一未变更片段已完整可见，仍反复读取：检查工具说明、信息冲突、提示词过于谨慎或模型行为。

读取次数高并不能单独证明上下文预算不足。修改前后的版本也不能简单按路径合并去重。

## 摘要与预算

核对压缩候选、旧摘要、参考信息、输出和安装检查。分别计算生成文本大小与装入完整请求后的大小；正文减少不代表完整请求一定能容纳。

区分：模型调用失败、格式失败、来源核验失败、收益不足、完整请求超预算。工具摘要与跨轮摘要可能拥有不同触发条件和更新位置，不能用其中一个成功推断另一个已更新。

短结果不摘要本身可能合理；但若它是尚未解决的关键测试失败，要检查离开原文窗口后是否存在信息缺口。旧摘要中的未完成状态也需要与后续写入和测试结果对照。

## 补丁失败

检查补丁 oldText 是否确实来自当次可用源文本、唯一匹配、版本是否变化，以及变化发生在本批次、前一批次还是外部。

整文件哈希不同不一定表示目标片段被改动，但仅凭片段仍存在也不足以证明修改安全。评估能否验证受控修改链和非重叠性；无法证明时保留拒绝并要求重新获取来源。
